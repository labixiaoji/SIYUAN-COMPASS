# 部署与运维文档

> 本文说明通用版本的本地 Docker 和标准生产部署。学校 `sjtu-production` 分支使用
> [学校部署说明](../deploy/部署记录.md) 中的 systemd、Nginx 和 `/shengya/` 配置。

## 1. 环境配置

项目只使用根目录 .env。先复制模板：

~~~bash
cp .env.example .env
~~~

至少配置：

~~~text
LLM_PROVIDER
KIMI_API_KEY 或 DEEPSEEK_API_KEY
AUTH_SECRET
ADMIN_PASSWORD
POSTGRES_PASSWORD
FRONTEND_ORIGINS
~~~

报告配额、任务租约、草稿保留和审计保留都在 .env.example 中有说明。真实密钥只放在服务器 .env，不提交到 Git。

## 2. 账户配额设置

账户配额是按账号、按自然日计算的功能使用次数限制，不是数据库容量限制。

默认不限制：

~~~text
REPORT_GENERATION_DAILY_LIMIT=0
~~~

设置为正数即可启用限制。例如：

~~~text
REPORT_GENERATION_DAILY_LIMIT=3
REPORT_GENERATION_QUOTA_TIMEZONE=Asia/Shanghai
~~~

- 报告配额按创建生成任务计数，任务成功、失败或取消都会占用一次。
- 删除报告、任务或其他业务数据不会返还当天已使用的额度。
- 到达上限时接口返回 429；下一个自然日自动重新计算。
- 修改 .env 后需要重启或强制重建后端容器。

## 3. 本地 Docker 开发

~~~bash
docker compose -f docker-compose.dev.yml up -d --build
docker compose -f docker-compose.dev.yml ps
docker compose -f docker-compose.dev.yml logs -f backend
~~~

访问：

- 前端：http://localhost:5173
- 后端：http://localhost:8000
- API 文档：http://localhost:8000/docs

停止开发容器：

~~~bash
docker compose -f docker-compose.dev.yml down
~~~

只有确认本地数据库无用时才使用 down -v，因为它会删除开发数据卷。

## 4. 服务器生产部署

首次部署：

~~~bash
cp .env.example .env
# 填写生产环境配置
docker compose up -d --build
docker compose ps
~~~

更新代码：

~~~bash
git pull origin main
docker compose up -d --build
~~~

只修改后端环境变量时：

~~~bash
docker compose up -d --force-recreate backend
~~~

生产前端由 Nginx 提供静态文件，后端和 PostgreSQL 不直接暴露公网。正式环境应在外层配置 HTTPS、域名、访问日志和备份策略。

## 5. 健康检查和日志

~~~bash
curl http://localhost/health
docker compose ps
docker compose logs --tail=200 backend
docker compose logs --tail=200 frontend
docker compose logs --tail=200 postgres
~~~

健康检查返回 status 为 ok 才表示后端进程可用；还需要检查 PostgreSQL、模型 API 和反向代理是否正常。

## 6. 构建依赖问题

后端 Dockerfile 已为 pip 配置清华镜像、300 秒超时和 10 次重试。完整构建日志：

~~~bash
docker compose --progress=plain build --no-cache backend frontend
~~~

如果出现 files.pythonhosted.org 或镜像源 ReadTimeoutError：

1. 检查服务器能否访问当前镜像源。
2. 如果学校有内部 PyPI 镜像，将 backend/Dockerfile 中的 -i 地址换成内部镜像。
3. 网络恢复后重新构建。
4. 构建成功后再执行 docker compose up -d。

这类错误通常是依赖下载超时，不是业务代码错误。

## 7. 数据和清理

- PostgreSQL 数据保存在 postgres-data volume。
- 后端启动时执行一次数据维护，运行期间每 24 小时执行一次。
- 云端草稿默认保留 30 天；失败或取消任务会保留脱敏恢复快照，成功后清理对应快照。
- 终态生成任务和失败恢复数据默认保留 30 天。
- 管理员审计日志默认保留 180 天。
- 账号每日配额在跨过自然日后清零。

本次管理员页面和后端接口发生代码变化，部署端需要重新构建后端与前端镜像。数据库由应用启动时自动补充 `assessment_drafts.source_job_id` 字段和任务队列索引，正式环境改动前应完成备份。管理员页面展示错误代码、失败阶段、供应商状态码和追踪编号；具体堆栈需要根据追踪编号查看服务日志。

升级到移除语音功能的版本时，应用启动会清理旧的语音配额字段；生产环境执行前请先备份 PostgreSQL。

报告生成默认使用 3 个 Worker，模型请求并发上限为 3，单次模型调用超时 600 秒，临时网络错误最多重试 2 次。对应环境变量为：

~~~text
GENERATION_WORKER_COUNT=3
LLM_MAX_CONCURRENCY=3
LLM_MAX_REQUESTS_PER_MINUTE=8
LLM_TIMEOUT_SECONDS=600
LLM_MAX_RETRIES=2
LLM_MAX_OUTPUT_TOKENS=10000
~~~

`LLM_MAX_OUTPUT_TOKENS` 是单次画像或报告请求的输出 token 上限，不是模型总上下文窗口。调整前应确认所选模型和供应商允许的最大值；长 JSON 仍应优先通过压缩提示词和列表长度来避免 `finish_reason=length`。

`LLM_MAX_CONCURRENCY` 控制同时占用模型调用槽位的任务数，`LLM_MAX_REQUESTS_PER_MINUTE` 控制模型请求的启动速率，二者相互独立。RPM 按 `60 / RPM` 秒平滑放行，画像、报告、质量修复和重试请求共用名额；设置为 0 可关闭。若供应商硬限制为每分钟 10 个请求，建议先设置为 8 或 9 留出重试和计时误差余量。当前限制是单个 backend 进程内的，多个后端进程或副本需要共享速率限制器。

当前单服务器只启动一个 backend 容器/进程；不要通过多个 Uvicorn worker 或多个 backend 副本来提高并发，否则每个进程会各自计算并发上限。增加服务器前应先设计数据库级全局模型名额。

正式环境需要定期备份 PostgreSQL，并定期验证备份恢复。备份文件也应按隐私要求保存和销毁。

## 8. 常见问题

### 容器启动后反复重启

先查看 backend 日志，重点检查 DATABASE_URL、POSTGRES_PASSWORD、AUTH_SECRET、管理员密码和模型 API Key。

### 前端能打开但接口失败

检查生产构建是否使用 /api，Nginx 是否代理 /api 到 backend，以及 FRONTEND_ORIGINS 是否包含实际访问地址。

### 报告生成失败

检查管理员“填写记录”页面中的生成状态、错误代码、失败阶段、供应商状态码和追踪编号，再结合 backend 日志定位。失败任务会保留问卷快照，修复配置后可从学生端恢复问卷重新提交。
